# EV07 – reelle importendringer og slettede frister

Lokal kandidat for [#117](https://github.com/depmartin/Budsjettkalender/issues/117)
på branch `codex/117-import-varsling`, base
`28694c580141b91f9707c616a53ee95f05246e11` (levert EV06/PR #135).
Hele #110 og #117 med kommentarer er lest sammen med AGENTS, ordliste,
standarder, arkitektur, status, relevante ADR-er og tidligere akseptanse.
Dette er byggerens kandidat før samlet review, separat sikkerhetsaudit,
publisering og faktisk kandidat-CI. Andre arbeidsflater er bevart.

## Observerbar atferd

Importens v1-kontrakt, fullstendige feltsett, forhåndsvisning, erstatt-alt,
AntallErstattet og eksisterende bekreftelses-/avbryt-/feilflyt beholdes.
Godkjent førtilstand med synlighet leses inne i importtransaksjonen og
sammenliknes per identitet med godkjent ettertilstand. Første publisering
gir Ny med ettermetadata; semantisk vesentlig endring gir Endret gjennom den
samme hendelsesbyggeren som direkte redigering og godkjenningskøen. Identisk
innhold, korrektur, endret grupperekkefølge og vilkårlig referansedag eller
klokkeslett i uendret tentativ måned gir ingen hendelse. Aldri publisert
innhold gir ingen fristpost.

Bortfall fra godkjent utvalg gir Slettet, som bruker Vesentlige endringer
og dens aktiveringsgrense. FoerJson bevarer siste publiserte tilstand;
EtterJson er null. Gruppekodene bevares relasjonelt uten avhengighet til
dagens frist eller grupperegister. Hele importen, begge saves, hendelser,
historiske grupper og publiseringssekvens fullføres eller rulles tilbake
samlet. Samme tjeneste kan forsøke på nytt med en ny operasjonskontekst.

Oppsummeringen SQL-filtrerer historisk synlighet før metadata leses, med
fersk egen mottakerrolle/grupper. Begge innholdskontroller bruker samme
regel. Bare eksplisitt atomisk Slettet kan beskrive en manglende frist;
Ny/Endret krever dagens godkjente synlighet. Tom historisk synlighet gir
bare administrator innsyn. Nytt bortfall eller gjeninnføring under siste
planlagring stanser overlevering av det innleste innholdet.

Sletting matcher siste hele år-/kategoriutvalg. Endret matcher hele før
eller hele etter, uten krysstreff. Hendelsene filtreres før gruppering,
forklaringer og nøyaktige plankoblinger. Slettingen tar ikke med tidligere
Endret-metadata som mangler dagens lesetilgang. Dags-/versjonsvern,
bekreftede hendelses-ID-er og stopp etter mulig overlevering består.

Ny-og-endret-og-fjernet etter aktivering før første oppsummering utelates
for alle tre varselvalg. En egen livssyklussekvens, uavhengig av senere
typevalg, og bekreftede hendelseskoblinger avgjør dette uten å vise skjult
historikk. Etablert frist før aktivering eller tidligere bekreftet Ny/Endret
kan senere få slettingsvarsel. Gjeninnført eksplisitt ID bruker siste bevarte
publiserte tilstand og eventuell Endret, uten en ekstra Ny eller ny identitet;
den livsvarige Ny-indeksen og historikken beholdes. Legacy uten Ny er prøvd.

Slettingslenken går til vanlig `/kalender` med budsjettår, kategori,
datoperiode og generell fjerningsmarkør. Tittel, notat, adresse, frist-ID,
JSON og token finnes ikke i lenken. Siden krever ordinær innlogging og
serverfiltrering. Den viser «Fristen er fjernet …» og det relevante utvalget,
også når årets siste frist er fjernet. Ingen avlysningsmodul er innført.

## Migrasjon og kompatibilitet

`20261029092000_HistoriskSlettingssynlighet` legger additivt til historiske
gruppekoder og Livssyklussekvens. Designer, snapshot og normal demooppgradering
følger samme skjema. EV02–EV05-demoer oppgraderes atomisk og idempotent.
Eksisterende frister utgjør installasjonens etablerte utgangspunkt;
eksisterende aktiveringsrader får dagens koordinasjonssekvens som
livssyklusgrense. Eldre typevalgs ukjente opprinnelige aktivering rekonstrueres
ikke. Type-/utvalgsgrenser, hendelser, planer og koblinger beholdes, uten
historiske hendelser eller grupper. Nye aktiveringer får eksakt databaseordnet
livssyklusgrense. Se begrunnelsen i ADR-0010.

Autentiske historiske testmodeller ignorerer kun de nye modellfeltene.
Oppgraderingsprøven starter fra EV05, bevarer tidligere data/planer og faktisk utvalgs-JSON, gjentas
og fullfører en ventende plan med legacy metadata. SQL Server har den samme
prøven gjennom faktisk migrasjonskjede. Up/Down, målmodell og snapshot
sammenliknes i ordinærporten. V1-JSON med tom ID og faktisk HTTP-fristeksport
prøves uten abonnentadresse, bekreftelsesdata, hendelser eller sendehistorikk.

Den eksisterende slettet-mål-prøven for godkjenning forventer nå den legitime
Slettet-hendelsen fra vellykket tom import. Den binder hendelse og sekvens før
den gamle godkjenningen slippes, og krever nøyaktig samme resultat etter
databasefeilen. Åpent forslag, manglende målfrist og tom innboks består.

Delte prøver omfatter semantisk vesentlighet og korrektur, blandet import,
upublisert før/etter, identisk gjenimport to ganger, tom import, legacy v1,
før-/etterutvalg og avvist krysstreff, filtrering før gruppering/forklaring,
FA/FAG/POL/admin/tomt publikum, slettet grupperegister, fersk tilbakekalling,
deaktivert konto og tilgangsfeil ved begge innholdskontroller. De prøver også
ny-og-fjernet for alle tre valg, tidligere sendt identitet, etablerte frister,
gjeninnføring med/uten Ny, abonnement/innhold/gjeninnføring under siste
planlagring og import mot aktivering/filterutvidelse i begge commitrekkefølger
med like eller bakovergående UTC-ticks. En reell trigger krever at DELETE,
hendelser, historiske grupper og INSERT faktisk finnes før den fremtvinger
feil. Rollback bevarer hele eksporten, hendelser, grupper og sekvens, og nytt
forsøk lykkes med samme tjeneste. Tom import har en egen reell triggerfeil.

De to nye nettleserforløpene bruker selvbetjent påmelding/adressebekreftelse,
faktisk nedlastet fristfil, endret fil, UI-forhåndsvisning/bekreftelse,
identisk import, Avbryt med tastatur, reell databasefeil og retry, jobbkjøring,
egen mottaker og slettingslenke. POL-innhold når ikke FAG-mottakeren. Sletting
av siste frist i 2045 beholder dette årsvalget i kalenderen. Vanlig innlogging
kreves også fra e-postlenken. Bredder er 390 og 1280 piksler.

Den samlede berørte nettleserporten bestod 133/133 på 11 minutter og 48 sekunder.
Den dekker alle kalender-, import- og kappløps-, fristnavigasjons-, tilgangs-,
påmeldings- og daglig e-postforløp. Nye sluttbilder av kalenderlenken er visuelt
lest i begge bredder, uten horisontal overflyt. Alle 344 scenarioer kreves fortsatt
i Chromium-CI; ingen uavklart bekymring i den berørte porten begrunner en full
lokal gjentakelse av de øvrige 211 scenarioene.

Etter denne brede kjøringen ble eksisterende semantisk sortering av tentative
frister beholdt med den samme Datoberegning-regelen, og EV05-oppgraderingsprøven
ble styrket til også å bevare faktisk utvalgs-JSON. Historiske gruppekoder
beholder dessuten dagens 64-tegns kontrakt, som kontrolleres i migrasjonsmodellen.
Tom import bruker en reell Slettet-innsettingstrigger; den blandede importens
trigger krever faktisk DELETE, historiske grupper/hendelser og INSERT før feil.
Disse avgrensede rettingene
følges av hele ordinærporten og alle 19 daglige e-postforløp på siste bygg;
kalender-/import-/tilgangsflatene har uendret kode fra den brede kjøringen.
Sluttkjøringene består med 1228/1228 og 19/19 uten feil/hopp. Begge nye
kalenderbilder fra siste runtime er visuelt lest. 441 backend-kildefiler og
194 runtimefiler er hashbundet før kjøringen; sluttkontrollen har null drift.
`backend-stability.json`, `runtime-stability.json` og kandidatmanifestet binder
de lokale bevisene til filene som leveres til orkestratoren.

Første nettleserforsøk hadde 0/2 bestått: testen forsøkte å bruke en forhåndsvisning
etter Avbryt. Den eksisterende kontrakten tømmer fil og forhåndsvisning. Testen
velger derfor filen på nytt etter kontroll av uendret faktisk eksport; 2/2 består.
Den første bildeserien hadde dessuten standardbredde etter personabytte. Sluttprøven
setter bredden på den faktiske mottaker-/kalendersiden. Tidlige feil er bevart.

Et tidlig baseline-forsøk startet bygging samtidig med egne pågående filendringer
og ga en kompilatorfeil. Den faktiske rød-prøven ble deretter kjørt mot stabilt
baseline-binary uten kodeendring under kjøringen. Sandbox-testhost stanset uten
resultat og ble avbrutt; den etterfølgende vanlige lokale kjøringen ga de to
forventede røde testene. Tidlig NU1900 er ingen bestått audit; alle tre senere
låste restore passerte med aktiv audit og null advarsler.

## Kjørekommandoer og gjenstående porter

Bruk SDK 10.0.402 fra global.json. Bygg før Kestrel-prøvene starter.

```powershell
dotnet restore backend/Aarshjul.slnx --locked-mode -m:1 -nr:false
dotnet build backend/Aarshjul.slnx -c Release --no-restore -m:1 -nr:false
dotnet test backend/Aarshjul.slnx -c Release --no-build
dotnet restore backend/Aarshjul.SqlServerTests --locked-mode -m:1 -nr:false
dotnet build backend/Aarshjul.SqlServerTests -c Release --no-restore -m:1 -nr:false
# Krever AARSHJUL_TEST_SQLSERVER mot master på en disponibel server:
dotnet test backend/Aarshjul.SqlServerTests -c Release --no-build
dotnet restore backend/Aarshjul.BrowserTests --locked-mode -m:1 -nr:false
dotnet build backend/Aarshjul.BrowserTests -c Release --no-restore -m:1 -nr:false
# Lokal Windows-prøve; CI bruker låst Chromium:
$env:AARSHJUL_BROWSER_CHANNEL = 'msedge'
dotnet test backend/Aarshjul.BrowserTests -c Release --no-build
```

Alle EV06-basens 1157/310/342 navn er bevart eksakt. Kandidaten legger til
71 ordinære, 69 SQL Server- og 2 nettlesertilfeller. Sammenlikningen bruker
ordinal, tegnsensitiv likhet. En innledende PowerShell-telling slo sammen to
allerede eksisterende navn med Kilde/kilde; tegnsensitiv telling har null
dubletter i både base og kandidat. CI-antallsvern er avstemt til 379/344,
med uendrede 15/20/45 minutter, hopp-/TRX-vern, aktiv audit og bare TRX-artefakter.

Det er ingen lokal SQL Server-tilkobling. Bygg og oppdagelse beviser ingen
SQL-kjøring. Samlet Standards-/Spec-review, separat sikkerhetsaudit og faktisk
full ordinær/ekte SQL Server/Chromium-CI gjenstår hos orkestratoren.
Edge/SQLite med kontrollerte adaptere beviser ikke Entra, gjestetilgang,
Azure SQL, M365 eller faktisk ekstern levering. Ingen produksjonsutsending,
utrulling, ekstern tilgangsendring, commit, push eller PR er utført av byggeren.
#110 og senere EV-tickets beholder sitt omfang.
