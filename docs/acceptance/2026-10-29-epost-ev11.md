# EV11 – avbrudd, samtidighet, sendefeil og driftsstyring

Arbeidsgrunnlag er #121 og hele #110 med nattplanen i kommentar 6505465238.
Kandidaten bygger på faktisk EV10-merge `461edae60a2ad335e9376612a636e16dbd85b395`,
tree `645297ac57c75f97f3cb4cb66b150df6f09b308e`. Dette dokumentet beskriver en lokal
kandidat før samlet review, separat audit, ny CI og publisering.

## Atferd og ansvar

`IDagligEpostoppsummering.KjorAsync` beholder den sammenhengende dagsjobben.
Norsk lokal dato, planens unike dagsnøkkel, status-/versjonsvern, atomiske
publiseringssekvenser, gjeldende synlighet og fersk mottakertilgang består.
Dagsskifte gir ingen blind gjentakelse av mulig overlevert innhold. Nye hendelser
etter dagens aksept venter til neste lokale dag. Bekreftet betyr transportaksept.

Infrastructure eier forsøksjournal, varig teller, retryfrist, oppslagspause og
tidsfestet UnderSending. Bare adapterens uttrykkelige garanti om sikkert usendt
gir Feilet med mulig retry. Generisk feil, kansellering og timeout etter mulig
mottak gir Uavklart. En ny instans behandler en gammel eller ukjent starttid
konservativt. Gjenopptakelse nullstiller ingen status eller forsøksbudsjett.
Feilet-planer beholder hendelseskoblinger for retensjonsvernet. Ved retry velges
dagens tillatte innhold og nøyaktige koblinger på nytt før synkront mottak.

`IEpostdrift` gir beskyttet status, stans/gjenopptakelse og opprydding.
`/admin/innstillinger/epostdrift` og `/api/admin/epostdrift` bruker eksisterende
administratorpolicy. Kretsen revurderer identitet/policy hver gang. Mutasjon
krever serverbundet aktør, versjon og uttrykkelig bekreftelse. HTTP krever JSON,
har begrenset kropp, no-store og ingen CORS. Feil eksponerer ingen leverandørtekst.
Den globale stansen bruker samme databaseordnede overleveringslås som avmelding
og EV10-stans. Kalender og publisering virker mens dagsutsending er stanset.

Epostdriftsvern er én additiv migrasjon med Designer/snapshot og idempotent,
atomisk demooppgradering. Alle historiske migrasjoner, inklusive begge
`20261029092000`-ID-ene, beholdes. Historiske testmodeller beskriver fortsatt
sine tidligere skjemaer. Ingen historiske forsøk eller hendelser tilbakefylles.

## Tekniske standarder og retensjon

Alle verdiene kan konfigureres under `DagligEpost` og valideres.

| Opsjon | Standard | Virkning |
| --- | --- | --- |
| MaksSendeforsoek | 3 | Varig tak over instanser og lokale dager |
| Retrypause | 00:05:00 | Minimum fem minutter etter sikkert usendt |
| Oppslagspause | 00:01:00 | Varig pause ved utsatt tilgang/transport, uten transportforsøk |
| Tilgangsfrist | 00:00:15 | Frist per autoritativt oppslag, høyst tre per mottaker/kjøring |
| Kvitteringsfrist | 00:00:30 | Avslutter venting uten blind retry av mulig mottak |
| ForsoeksdetaljerDager | 30 | Gamle aksepterte detaljer og foreldede avmeldingshasher |
| HistoriskInnholdDager | 90 | Bare trygt overflødig historisk innhold |
| Ryddebatch | 100 | Høyst så mange endringer per atomisk batch |

Jobben rydder ved start og deretter hver time. Manuell demokjøring bruker samme
operasjon. Utløpt bekreftelsesmateriale fjernes uten å nullstille kvote,
forsøksantall eller aktiveringsgrenser. Bekreftelseskandidater strømmes for
SQLite-kompatibilitet: antall skriv er begrenset, mens kandidatskannet kan være
større. Samtidighets-/lagringsfeil ruller hele batchen tilbake; neste kall kan
gjentas. Første Ny-identitet, siste nødvendige historiske tilstand, historisk
slettingssynlighet, planer, dagsnøkler og behandlingskoblinger beholdes.

Ubehandlet, sikkert Feilet og Uavklart med nødvendig historikk/forsøksdata
beholdes uansett alder. Gjeldende påmeldingsperiodes avmeldingshash beholdes
også uansett alder, slik at gamle e-postlenker fortsatt virker. Funksjonelle
unntak kan derfor gi lengre oppbevaring enn de tekniske daggrensene. Det finnes
ingen naiv sletting av gamle plan-/hendelsesrader, generell retry-reset eller
ubestilt manuell frigivelse av Uavklart. Uttømt budsjett vises i driftsstatus
og beholder hendelsene til senere avklart operatørhåndtering.

Null oppslagspause er et uttrykkelig kontrollvalg i de eksisterende
Application-/nettleserprøvene som bytter adaptertilstand uten å flytte klokken.
Egen EV11-kontrakt prøver standardpausen over nye instanser. Produksjonsvertsstart
avviser mindre enn ett minutts oppslagspause. De tekniske verdiene er standarder
for testadapterleveransen og er ikke godkjent produksjonspolicy.

## Etterprøving og bevisgrense

Rød reproduksjon av `EV11_sikkert_usendt_skilles_fra_mulig_overlevering` ga
forventet Feilet, faktisk Uavklart. Grønn prøve bekrefter eksplisitt adapterutfall.
Rød `EV11_utsatt_tilgang_har_varig_begrensning_av_nytt_oppslag_over_instans` gjorde
to oppslag i stedet for ett. Grønn prøve viser varig pause og nytt oppslag ved
fristen. Begge røde TRX-er beholdes i `TestResults/ev11/red*`.

Den delte `EpostdriftKontrakt.cs` kjøres ved samme offentlige grense i ordinær
SQLite-suite og SQL Server-suite. Den dekker retry før/ved frist, uttømt budsjett
over nye instanser/dager, samtidige instanser, fersk tilgang/inaktiv konto/
kildefeil, avmelding, administratorstans, adresse/filter og global driftsstans
mellom sikker feil og retry. Kontrollklokke/timer og barrierer prøver begrenset
tilgangs-/kvitteringsventing, kansellering, konservativ omstart, begge ordninger
av SQL-lås og synkront mottak, aktive abonnenter ved vårgap/høstoverlapp,
retensjon med akseptert og ventende sammen, sletting/gjeninnføring/ny-og-fjernet,
gamle avmeldingslenker og idempotens/rollback. Basens eksisterende kontrakter
og alle assertions beholdes. Egen HTTP-/kretskontrakt prøver administrator,
anonym/leser/bidragsyter/FA, nedgradering, JSON, no-store og trygge feil.

Fire nye reelle Kestrel/Blazor-scenarioer omfatter 390/1280 px og tastatur,
påmelding/bekreftelse → publisering → global stans → kalender/publisering under
stans → ingen mottak → omstart/gjenopptakelse med etterslep, samt omstart ved
sikker sendefeil og under kvitteringsventing. Lokal nettleser er Edge/SQLite;
full Chromium og ekte SQL Server kreves på ny kandidat i CI. Lokal SQL-tilkobling
er ikke konfigurert (`AARSHJUL_TEST_SQLSERVER` mangler); SQL-suiten bygges og
oppdages lokalt uten at dette påstås å være faktisk SQL-aksept.

Prosesslokal StartupHook i disponible testhostprosesser gir både lokal og
invariant VSTest-discovery. Ingen global Windows-kultur eller xUnit-innstilling
endres. Basens 1404/510/414 eksakte navn sammenlignes med ny discovery i begge
modi før CI-TRX brukes. Forventningslister, DLL-hasher og kulturproveniens ligger
i `TestResults/ev11/culture-discovery`; tidligere røde/grønne bevis bevares.
Endelig uavhengig discovery gir **1447 ordinære / 537 SQL Server / 418 browser**
i både lokal og invariant modus, med alle basens navn bevart og null dubletter.
Det er henholdsvis 43/27/4 nye navn. Forventningslistene er skrevet før noen
EV11-CI-TRX er lest. `candidate-final/*-invariant-names.txt` er de eksakte
forventningslistene for senere CI-verifikasjon; `final-inventory-proof.json`
binder dem til begge discoverymodi og test-DLL-hasher. Basens 20 kulturavhengige
DateOnly-navn beholdes i hver modus uten normalisering av CI-resultater.
CI beholder 15/20/45 minutter, aktiv pakkeaudit, hemmelighetssøk og bare-TRX-
artefakter. Bare SQL-/browserantall oppdateres etter faktisk discovery.

Endelig lokal ordinærport består **1447/1447**, null feil/hopp. **10/10** berørte
reelle Edge/Kestrel-forløp består, inklusive alle fire nye EV11-scenarioer.
Låst restore og Release-bygg av ordinær, SQL Server og browser består uten
byggeadvarsler. Repoets uendrede hemmelighetskontroll består for begge endelige
TRX-er og begge tilsiktede røde reproduksjoner. Eksakt binding og TRX-hasher ligger
i `TestResults/ev11/final-test-proof.json`; SQL-/miljøgrensen ligger i
`environment-boundary.json`. Samlet review, separat audit og faktisk ny SQL-/
Chromium-CI gjenstår. Dette er ingen attestasjon av de senere portene.

Ingen produksjonsadapter, ekstern prøvepost, tilgangsendring eller utrulling
inngår. D1–D5 og EV12–EV14 står åpne. Kontrollerte mottak, transportaksept,
lokal Edge/SQLite eller grønn CI beviser ikke faktisk Entra/Azure/M365-levering.

## Retting etter samlet review, 29. oktober 2026

Bevisene og «endelig»-tallene ovenfor gjelder den opprinnelige kandidaten
`7a34c296a45439905df309c63d1487262779892e`, tree
`4ce6b29b89a6f689240e5c9c8f4f089f0ed81e7c`. De gamle bevisene beholdes.
Nye bevis for rettingen ligger separat i `TestResults/ev11/review-fix/`.

Standards P2 er konkret reprodusert gjennom `IDagligEpostoppsummering.KjorAsync`
og `IEpostdrift.HentAsync` mot nye disponible databaser. Den nye delte prøven
`EV11_sikkert_usendt_avklarer_observerende_instans_uten_aa_avbryte_resten_av_jobben`
kjøres med både synkront og asynkront sikkert-usendt-utfall. En styrt klokke med
egne tilgangs-/kvitteringstimere og barrierer lar siste tilgangsforløp bruke
14 sekunder før transportstart. En annen instans observerer ved claim-alder
31 sekunder; transportens egen kvitteringsventing har da bare brukt 17 av 30
sekunder. Den andre instansen lagrer Uavklart for samme plan og forsøk.
Den synkrone varianten holder lagring av det allerede kjente sikre utfallet
ved en databasebarriere; den asynkrone varianten får det sikre utfallet etter
observasjonen. Før retting kastet begge variantene
`DbUpdateConcurrencyException` ved lagring av Feilet og avbrøt dagsjobben.
`red-final/` binder siste testkilde og DLL-er til den opprinnelige
produksjonsfilens eksakte Git-blob. Ingen historiske SQLite-bevis åpnes.

Senderen leser nå samme plan og forsøksrad på nytt ved den konflikten. Bare
Uavklart med samme forsøksnummer og bevarte primærnøkler kan bli Feilet med
retryfrist og fjernet sikkert-usendt avmeldingsrett. Bekreftet, manglende
forsøk eller et nyere forsøksnummer får ingen slik omskriving. Hendelseskoblinger
beholdes. Prøven viser Feilet i driftsstatus, varig forsøksnummer 1, fem minutters
retryfrist, resultat også for neste mottaker, ingen tidlig retry, én senere
aksept og bevarte Feilet/Bekreftet-journalrader uten dobbel mottakelse.
Eksplisitt sikkert-usendt-garanti er fortsatt eneste grunnlag for denne retryen.

Standards P3 om duplisert modellutelatelse er vurdert. `FasedataBevis.cs` lenkes
også inn i browserprosjektet, som ikke har `EpostoppgraderingBevis` eller dens
`Epostdatabase`-avhengighet. Direkte gjenbruk er derfor ikke kompatibel med
dagens prosjektgrenser. Den lille utelatelsen beholdes, fremfor å utvide denne
samtidighetsrettingen med nye delte testmoduler. Historiske modeller,
migrasjoner og migrasjons-ID-er er uendret.

Ny uavhengig discovery i både lokal og invariant prosesskultur gir
**1449 ordinære / 539 SQL Server / 418 browser**. Alle opprinnelige
1447/537/418 navn og alle basens 1404/510/414 navn er bevart eksakt i hver
modus, uten dubletter. De to nye teoritilfellene finnes i både ordinær og
SQL-kontrakt. Nye forventningsfiler er skrevet før noen EV11-CI-TRX leses.
De ligger i `review-fix/culture-discovery/*-invariant-names.txt`;
`inventory-proof.json` og `discovery-runs.json` binder navn, testhostkultur og
lastede DLL-hasher. Den eksisterende EV10-hooken brukes bare i disponible
testhostprosesser. Brukerkultur og `Verify-CiTrx.ps1` er uendret.
CI endrer bare SQL-antallet til 539 ut fra denne discoveryen; browser forblir
418. Audit, hemmelighetsvern, bare TRX og 15/20/45 minutter består.

Etter siste kodeendring består full ordinærsuite **1449/1449**, med null
feil/hopp. Alle fire berørte EV11-scenarioer består på nytt i ekte lokal
**Edge/Kestrel/SQLite: 4/4**. Begge nye raceprøver er grønne, og siste røde
reproduksjon mot den opprinnelige produksjonsfilen har 2/2 tilsiktede feil
av nøyaktig samme konkurransegrunn. Låst restore og Release-bygg for alle tre
prosjektene består, med null byggeadvarsler/feil. SQL Server er fortsatt bare
bygget/oppdaget lokalt. `final-proof.json` binder kildefiler, DLL-er, nye
forventningslister og TRX-er; repoets uendrede hemmelighetskontroll brukes
på de nye TRX-ene. Hele ordinærsuiten inkluderer e-post- og oppgraderingssamspill.

Ny relevant gjennomgang og faktisk kandidat-CI med SQL Server og Chromium
gjenstår etter rettingen. Tidligere review-/auditresultater attesterer ikke
denne endrede kandidaten. D1–D5, produksjonsadaptere og ekstern levering
forblir utenfor den lokale rettingen.
