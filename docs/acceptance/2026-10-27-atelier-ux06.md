# Atelier UX06 – forslag fra kalenderdato til godkjent frist

Lokal kandidat for [#81](https://github.com/depmartin/Budsjettkalender/issues/81),
27. oktober 2026. Base: `b1404d87f108854a535e307db33787b35f1e9e20`, den mergede
UX05-leveransen i [PR #100](https://github.com/depmartin/Budsjettkalender/pull/100).
Hele [#75](https://github.com/depmartin/Budsjettkalender/issues/75), #81 og aktuelle
kommentarer er lest. Den godkjente grønne Atelier-referansen videreføres.

## Implementert atferd

FA og andre eksisterende bidragsytere kan velge Foreslå frist i dagsagendaen.
Skjemaet åpnes i samme dialog med redigerbar dato fra den valgte dagen. Ett valgt
budsjettår kan forhåndsutfylles; ellers brukes neste budsjettår etter appens Oslo-dato.
Datoen bestemmer ikke budsjettåret. Tentativ måned bruker en månedsvelger og
eksisterende presisjon med valgfri primo, medio eller ultimo. Forslaget får ingen
automatisk foreslått synlighet fra kalenderfiltre eller andre frister, og har ikke
et nytt felt for klokkeslett.

Forslagsskjema gjenbrukes av kalenderdialogen og de tre dedikerte inngangene
`/forslag/ny`, `/forslag/endre/{fristId}` og `/forslag/{id}/rediger`.
IForslagsinnsending, innsenderidentitet, eierskap, varsler og IGodkjenningsko er
beholdt. Kvitteringen sier Venter på behandling og lenker til Mine forslag.
Kalenderperiode, årsvalg, kategorier og søk består ved avbryt og innsending.

Valideringsfeil og teknisk lagringsfeil beholder den utfylte registreringen og gir
en fokusert norsk feilmelding. En tømt eller ugyldig månedsvelger forblir tom og
avvises ved innsending; siste gyldige dato brukes ikke som reserve. En ny gyldig
måned kan velges og sendes med de øvrige feltene beholdt. Innsending sperres før første ventepunkt, under
lagring og etter suksess, slik at allerede køede hendelser ikke oppretter flere
forslag. Dette er en skjerm-/hendelsessperre, uten en ny idempotensordning i lagringen.
Lukk, Avbryt og Escape kan ikke avbryte en pågående lagring.

ErBidragsyter kontrolleres i serverhendelsen før åpning og innsending, i tillegg
til at AuthorizeView skjuler handlingene. Endringsforslag kontrollerer tilgang til
originalfristen ved lasting og innsending. Administratoren beholder direkte
fristforvaltning og godkjenningsansvar. POL velges fortsatt aktivt ved publisering,
mens et endringsforslag bevarer originalfristens eksisterende synlighet.

## Observerbare prøver

Åtte nye scenarioer i KalenderforslagTester bruker ekte Kestrel, Blazor-krets og
Playwright. All utfylling og behandling skjer i appen; Mine forslag, køen og
lese-API er de offentlige observasjonsgrensene.

| Prøve | Kontrollert utfall |
| --- | --- |
| FA og FIN-FAG, to hovedscenarioer | Valgt 20. november 2030 forhåndsutfylles og kan endres til 21. november. Budsjettår 2032, Gul bok, notat og foreslått synlighet følger til Mine forslag og køen. Ingen ordinær frist finnes før administratorgodkjenning. Etterpå finnes nøyaktig én GUID, med samme dato, år, kategori, notat og dags-/månedspresisjon i Kalender, Tidslinje og Fristliste. |
| POL ved ny frist | Ingen foreslått gruppe er forhåndsvalgt. Bidragsyterens aktive POL-forslag vises i køen, men POL er av ved administratorens godkjenning og følger ikke stille med i publisert synlighet. |
| Tentative måneder | Ingen kvalifikator, primo, medio og ultimo gjennomføres fra kalenderdag til desember 2030, godkjenning og alle tre presentasjoner. Månedspresisjon og kvalifikator består uten falsk dagsdato eller Heldag-tekst. |
| Validering og kontekst | Ett valgt år forhåndsutfylles. Tom tittel gir fokusert feil og beholder redigert dato, år, kategori, notat og synlighet. Avbryt går tilbake til dagsagendaen; Escape returnerer fokus til valgt dag. Periode, søk, årsvalg og kategorier består også etter vellykket innsending. |
| Reell lagringsfeil | En disponibel SQLite-trigger avviser INSERT med en intern markør. UI viser trygg Prøv igjen-melding, beholder feltene og fokus, og eksponerer ikke markøren. Etter fjerning av triggeren kan samme registrering sendes og gir én rad i Mine forslag og køen. |
| Køede innsendinger | En skrivelås holder den faktiske lagringen tilbake mens tre submit-hendelser sendes. Send inn, Lukk og Avbryt er deaktivert og Escape beholder dialogen. Etter frigivelse finnes nøyaktig ett ventende forslag i Mine forslag og køen, og ingen publisert frist. |
| Leser og administrator | Ingen forslagshandling i agenda eller detaljer. Direkte HTTP-kall til alle tre forslagsinnganger avvises. Administratorens eksisterende direkte editor lagrer endring på samme frist-ID. |
| Endringsforslag | Fra synlig detalj lastes originalt innhold uten synlighetsvalg. Originalfristen står uendret før godkjenning. Etterpå har den samme GUID og nøyaktig samme FA/POL-synlighet, og endret innhold vises i alle tre presentasjoner. |

Fire nye HTTP-tilfeller i NavigasjonHttpTester prøver alle tre dedikerte innganger
uten å bruke UI-navigasjon. Anonym gir 401, leser og administrator gir 403 og ingen
skjemafelter, mens bidragsyter gir 200. Dette er faktisk serveravvisning ved den
eksisterende HTTP-grensen. Det er ingen ny test-POST-port eller test av private
komponentmetoder. Serverhendelsenes tilleggssjekker inngår også i samlet review/audit.

De 47 tidligere nettleserscenarioene beholdes. Tre tidligere rolleprøver bruker nå
knappen Foreslå endring i den felles dialogen; innhold, tilgang og utfylling prøves
fortsatt. Eksisterende dedikerte innsending-/endrings-/revisjonsinnganger og
avvisning, varsling, eierskap, gammel køfane og godkjenning er med i regresjonene.
De ordinære Application- og SQL Server-kontraktene er beholdt.

En ny regresjon i ForslagTester bruker det samme skjemaet via `/forslag/ny`:
20. november 2030 → Måned → tøm måned → send med gyldige øvrige felter. Den
kontrollerer fokusert norsk feil og bevarte felter, ingen rad i Mine forslag/køen
og ingen publisert frist. Etter valg av desember 2030 sendes registreringen én
gang; godkjenning gir 1. desember som intern månedsdato med månedspresisjon,
medio, budsjettår 2032 og beholdt notat. Alle observasjoner bruker UI og lese-API.

## Rød → grønn

`TestResults/81-red/ux81-red.trx` viser den første reelle prøven før UI-endringen:
1 av 1 feilet fordi dagsagendaen manglet Foreslå frist. Den samme kalenderinngangen
er deretter utvidet til de to komplette hovedscenarioene.

`TestResults/81-green/ux81-green2.trx` fanget en faktisk feil ved teknisk lagringsfeil:
en tidligere render kunne fullføre før feilelementets referanse var tilgjengelig.
Fokusforsøket brøt Blazor-kretsen. UI-rettingen venter på at aktuell feil har vært
med i en fullført render og at elementreferansen er konfigurert.
`TestResults/81-green/ux81-storage-green.trx` bekrefter samme triggerprøve grønn,
inklusive fokus, bevarte felter, trygg feil og vellykket nytt forsøk.

`TestResults/81-green/ux81-green3.trx` har de øvrige sju nye nettleserscenarioene
grønne, og `TestResults/81-green/ux81-http.trx` har alle fire nye HTTP-tilfeller
grønne. Tidlige prøveforventninger ble korrigert til køens eksisterende datoformat,
API-ens numeriske enumverdier og faktisk tilgjengelige årsvalg, uten endring i
produksjonskontraktene.

Reviewregresjonen `TestResults/81-review-month/ux81-review-month-red.trx` feilet
før rettingen: Mine forslag viste en utilsiktet rad med 01.11.2030 etter tømt
månedsfelt, og feilmeldingen manglet. Den samme prøven er grønn i
`TestResults/81-review-month/ux81-review-month-green.trx` etter rettingen.

## Samlet review og sikkerhetsaudit

Orkestratorens tre separate gjennomganger vurderte hele kandidaten
`6757f1d397c124be50fd9113534836d3c9dccd03` mot base `b1404d87f108854a535e307db33787b35f1e9e20`.
Standards-review fant ett P2: tømt månedsfelt lot gammel dato bli sendt.
Spec-review fant samme P2 og ett P3: bildestien nedenfor pekte feilaktig til
kjøringens app-/databasemappe. Separat sikkerhetsaudit fant ingen funn; dens
107 målrettede prøver passerer i `TestResults/81-security/ux81-security.trx`.
Denne oppfølgingen retter P2 og P3. Etterkontroll av den rettede kandidaten er
ikke utført av byggeren og er fortsatt orkestratorens port før publisering.

## Sluttkontroll og visuell kontroll

Etter siste kilde- og testendring passerer **643 ordinære tester og 56 reelle
Edge/Kestrel-scenarioer, 0 feil og 0 hopp**. Alle 639 ordinære og 47 nettleserprøver
fra forgjengeren er med. Hovedscenarioet er i sluttprøven skjerpet til budsjettår
2032 på dato i 2030, slik at automatisk utledning av budsjettår fra dato ikke kan
gi et falskt positivt resultat.

Sluttresultatene etter reviewretting er `TestResults/81-review-final/ux81-review-final-ordinary.trx` og
`TestResults/81-review-final/ux81-review-final-browser.trx`, med byggeloggen
`TestResults/81-review-final/ux81-review-final-build.log`. SDK 10.0.402, låst restore og Release-bygg av
ordinær løsning, BrowserTests og SqlServerTests er gjennomført. Sluttbyggene har
ingen feil eller advarsler. Sårbarhetskontroll er aktiv; en tidlig sandbox-restore
ga nettverksavhengig NU1900, som er borte etter tvungen restore med nettverkstilgang.
Ingen kontroll er deaktivert. CI og utviklingsveiledningen krever nøyaktig
56 beståtte nettleserscenarioer uten hopp. Alle 55 scenarioer fra kandidaten før
reviewrettingen er bevart; regresjonen for tømt månedsfelt kommer i tillegg.

En separat UI-bygger har tatt og åpnet alle 30 faktiske bilder med view_image i
`TestResults/81-visual/` (PNG-filene ligger direkte i denne mappen). Kjørings-ID
`run-1793124811606` i manifestet identifiserer app-/databasemappen, ikke en
undermappe med bilder. De viser desktop 1440 × 1000 og mobil
390 × 844 med tom agenda, skjema, valideringsfeil, kvittering og endringsforslag for
FA/FIN-FAG, samt agenda/detaljer for leser og administrator. Feil- og avbrytprøvene
har synlig fokus. Lange skjemaer ruller i dialogen, og ingen side eller dialog har
horisontalt overløp. Atelier-palett, Segoe UI, fire ruter og eksisterende skall består.
`TestResults/81-visual/capture-result.json` har tom feilliste og breddeobservasjoner
for alle tilfeller. Ingen abonnementsside eller token-URL er fanget.

Reviewrettingens tomme månedsfelt og bevarte utfylling er også åpnet med view_image
ved desktop 1440 × 1000 og mobil 390 × 844. De to ekstra PNG-filene er
`ux81-empty-month-desktop.png` og `ux81-empty-month-mobile.png` under
`TestResults/81-review-month-apps/41d4f694206a4119bc61fa00ed0ef49a/`.
Feilmeldingen og alle feltene er lesbare på begge bredder, uten horisontalt overløp.

## Gjentaking og bevisgrenser

Bruk SDK 10.0.402 i global.json og [utviklingsoppsettet](../development.md).

```powershell
dotnet restore backend/Aarshjul.slnx --locked-mode
dotnet restore backend/Aarshjul.BrowserTests/Aarshjul.BrowserTests.csproj --locked-mode
dotnet restore backend/Aarshjul.SqlServerTests/Aarshjul.SqlServerTests.csproj --locked-mode
dotnet build backend/Aarshjul.slnx -c Release --no-restore -m:1 -nr:false
dotnet build backend/Aarshjul.BrowserTests -c Release --no-restore -m:1 -nr:false
dotnet build backend/Aarshjul.SqlServerTests -c Release --no-restore -m:1 -nr:false
dotnet test backend/Aarshjul.BrowserTests -c Release --no-build --filter FullyQualifiedName~KalenderforslagTester
dotnet test backend/Aarshjul.Tests -c Release --no-build --filter FullyQualifiedName~Forslagsinnganger_avviser
dotnet test backend/Aarshjul.BrowserTests -c Release --no-build --filter FullyQualifiedName~Tom_maaned_avvises
dotnet test backend/Aarshjul.slnx -c Release --no-build --logger 'trx;LogFileName=ux81-review-final-ordinary.trx' --results-directory TestResults/81-review-final
dotnet test backend/Aarshjul.BrowserTests -c Release --no-build --logger 'trx;LogFileName=ux81-review-final-browser.trx' --results-directory TestResults/81-review-final
```

Lokalt brukes AARSHJUL_DOTNET med full SDK-bane og AARSHJUL_BROWSER_CHANNEL=msedge.
Databaser, app-logger, bilder og scripts i TestResults er ignorert lokal evidens.
Dette er SQLite/Edge-bevis. SQL Server-prosjektet bygges lokalt; ekte SQL Server og
Chromium er fortsatt obligatoriske CI-porter. Samlet Standards-/Spec-review og
separat sikkerhetsaudit håndteres av orkestratoren før publisering og merge.
Demo beviser ikke Entra, Azure SQL, M365 eller pilotakseptanse med brukere.
#82 og senere er utenfor denne kandidaten. Ingen deploy er utført.
