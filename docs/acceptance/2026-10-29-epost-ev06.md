# EV06 – fristvarsling fra godkjenningskø og genererte forslag

Lokal kandidat for [#116](https://github.com/depmartin/Budsjettkalender/issues/116),
med hele [#110](https://github.com/depmartin/Budsjettkalender/issues/110) og
kommentarene som kravkontekst. Isolert branch `codex/116-ko-varsling` bygger på
levert EV04, EV05 og UX18, main `29421c2ff1a1595ecfaba5e80d18ce529ade8c03`.
Dette er byggbevis før orkestratorens samlede review, separate sikkerhetsaudit,
publisering og faktiske kandidat-CI. Andre arbeidsflater er bevart.

## Atferd og avgrensning

Begge innganger på `IGodkjenningsko` bruker den eksisterende felles
publiseringsoperasjonen. Nye bruker-, robot- og genererte forslag får én Ny med
ettermetadata ved første publisering. Endringsforslag får Endret med faktisk
innlest førtilstand og publisert ettertilstand ved semantisk vesentlig endring.
Innsending, generering/regenerering, avvisning og uendret innhold/korrektur gir
ingen fristpost. Innsenders ordinære innboksmelding består ved godkjenning og
avvisning, også uten e-posthendelse.

En liten felles hendelsesbygger for kø og direkte administratorredigering
bruker `Fristtilstand`. Endret dato, tid, presisjon, tentativ måned/kvalifikator,
budsjettår eller kategori er automatisk vesentlig. Annen faktisk innholdsendring
kan markeres av administrator med forklaring på 1–300 tegn. Identisk tilstand,
blank/for lang forklaring og kontrolltegn avvises ved manuell markering.
Godkjennerens valg finnes på kortet og ved justering av endringsforslag;
det nullstilles ved ny bekreftelse og gir ingen ny rettighet til bidragsyteren.

Endringsforslag beholder målfristens synlighet, opphav, kilde og dokumentkobling.
Robotforslagets dokumentkobling og originale uttrekksbevis bevares. Direkte
godkjenning bevarer målfristens klokkeslett ved dagspresisjon; justering
prefyller tiden og kan endre eller tømme den. Månedspresisjon har ingen tid.
Nye forslag er heldags ved direkte godkjenning og kan få tid ved justering.
Ingen ny forslagskolonne, migrasjon, genereringsmodell eller produksjonsadapter
er nødvendig.

Forslagets status/justerte felter, frist, synlighet, innboks, hendelse og
publiseringssekvens lagres i samme transaksjon. Den eksisterende smale
Forslag-konfliktoversettelsen består. Slettet mål eller samtidig endret
målinnhold beholder databasefeilen og ruller tilbake behandlingen, uten feil
førmetadata eller ekstra hendelse. Samme tjeneste kan forsøke på nytt med en
ny operasjonskontekst.

EV05-utvalg brukes uendret: hele før eller hele etter, filtrering før gruppering
og forklaring, dagens synlighet og fersk tilgang før postadapteren. Både
adresseaktivering og filterutvidelse ordnes mot køpublisering etter faktisk
commit, også ved like eller bakovergående UTC-ticks.

Delte `DagligEpostKontrakt` prøver begge godkjenningsinnganger, faktiske mottakere
og tekst/HTML, alle tre varselvalg, semantikk og korrektur, manuell validering,
varig lesing fra ny jobb, robotspor og faktisk generering/regenerering/avvisning.
Utvalgsprøver dekker inn-/utflytting, avvist krysstreff, filtrering før gruppering,
utelatt historisk forklaring, POL og ferskt tilbakekalt tilgangsgrunnlag.
Begge commitrekkefølger ved adresseaktivering og filterutvidelse prøves med
like og bakovergående UTC-ticks for begge køinnganger.

Delte `GodkjenningskonkurranseKontrakt` prøver ny og endring gjennom begge
innganger, to godkjenninger, godkjenning/avvisning i begge rekkefølger, gammel
behandling etter ny innsending, slettet mål og samtidig målredigering.
Databasetriggere krever at de relevante faktiske skrivene allerede finnes i
transaksjonen før de fremtvinger feil. Rollback av forslag/justering, frist,
synlighet, innboks, hendelse og sekvens kontrolleres før nytt forsøk på samme
tjeneste. Alle disse prøvene er også kompilert inn i SQL Server-porten.

De seks nye nettleserforløpene bruker faktisk påmelding/adressebekreftelse,
innsending/generering, godkjenning/justering, jobbkjøring og kontrollert mottaker.
De dekker Ny, begrunnet tekst, automatisk datoendring, gammel annen fane uten
ekstra post, avvisning, regenerering og utelatt POL-innhold. Fire tilfeller
prøver nye felter i 390 og 1280 piksler, tastatur, serverfeil og nullstilling av
kort. Fire tokenfrie bilder av nye felter er visuelt inspisert; ingen horisontal
overflyt er observert.

Første nettleserforsøk hadde 2/6 grønne og 4 feil: den nye kontrollen av Mine
forslag traff både tidligere godkjent og ny ventende rad med samme tittel.
Kontrollen krever nå nøyaktig én ventende rad, med tidligere behandlingshistorikk
bevart. Ny samlet kjøring av de seks består. En tidlig HTML-forventning krevde
ukodet norsk bokstav i ellers kodet HTML; forventningen krever nå de konkrete
kodede taggene og fravær av rå tagg. De tidlige feilene er bevart som historikk.

Første bredere kjøring hadde 58/60 bestått, to feil og ingen hopp
(`browser-verified.trx`). Eksisterende
`TilgangTester.Atelier_administrasjon_samler_seks_virksomme_omraader_og_bevarer_direktelenker`
ble stående med interaktiv-markøren venter innen femsekundersgrensen. Årsaken er
ikke fastslått. Den nye justeringsprøven på mobil kunne dessuten klikke i gammel
fane før første fanes publisering var kvittert. Prøven venter nå på tilbakekomst
til køen og at det behandlede kortet er fjernet før gammel fane prøves. Dette
styrer rekkefølgen med et faktisk UI-utfall, uten å endre produktkode eller
tidsgrenser. Begge feil og den første kjøringen beholdes som historiske bevis.

Et byggforsøk mens nettleserprosessen brukte Webs Application-DLL feilet med
MSB3026/3027/3021. Bygg og nettleserprøver kjøres deretter sekvensielt.
Alle tre sluttbygg har null advarsler/feil. Feilen i den første bredere
nettleserkjøringen tilskrives ikke dette uten videre bevis.

Ny samlet etterprøve på stabile sluttfiler bestod **60/60** på 5 minutter og
42 sekunder. Den inkluderer alle 22 e-postforløp, forslag, generering og dens
initialisering, køens kildefilter, fristnavigasjon/redigering, kalenderforslag
og tilgang. Begge tidligere feiltilfeller består. Ingen ny produktfeil eller
uavklart bekymring er observert i etterprøven, så full lokal 342-port er ikke
gjentatt. Alle 342 Chromium- og 310 ekte SQL Server-tilfeller kreves fortsatt
i kandidat-CI. Backend- og runtimehashene er kontrollert uendret gjennom
sluttverifikasjonen (`backend-stability.json`, `runtime-stability.json`).

## Gjenstående porter og bevisgrenser

Kjør fra repo-roten med SDK 10.0.402 fra `global.json`. Bygg før nettleserporten,
slik at ingen Kestrel-prosess holder filene som byggingen skal oppdatere.

```powershell
dotnet restore backend/Aarshjul.slnx --locked-mode -m:1 -nr:false
dotnet build backend/Aarshjul.slnx -c Release --no-restore -m:1 -nr:false
dotnet test backend/Aarshjul.slnx -c Release --no-build
dotnet restore backend/Aarshjul.SqlServerTests --locked-mode -m:1 -nr:false
dotnet build backend/Aarshjul.SqlServerTests -c Release --no-restore -m:1 -nr:false
# Krever AARSHJUL_TEST_SQLSERVER mot master på disponibel server:
dotnet test backend/Aarshjul.SqlServerTests -c Release --no-build
dotnet restore backend/Aarshjul.BrowserTests --locked-mode -m:1 -nr:false
dotnet build backend/Aarshjul.BrowserTests -c Release --no-restore -m:1 -nr:false
# Lokal Windows-prøve; CI bruker låst Chromium:
$env:AARSHJUL_BROWSER_CHANNEL = 'msedge'
dotnet test backend/Aarshjul.BrowserTests -c Release --no-build
```

Samlet Standards-/Spec-review, separat sikkerhetsaudit og faktisk ordinær/ekte
SQL Server/Chromium-CI gjenstår hos orkestratoren. CI-antallsvern er avstemt med
faktisk oppdagede **310 SQL Server- og 342 Chromium-tilfeller**. Alle basens
**1063/216/336** navn er bevart, med 94/94/6 nye. Hoppvern, manglende-TRX-vern,
asserts, audit, bare-TRX-artefakter og tidsgrenser på 15/20/45 minutter består.

Ingen lokal SQL Server-tilkobling er konfigurert. Bygg og oppdagelse beviser
ingen SQL-kjøring. Endringen har ingen ny migrasjon; eksisterende skjema-/
oppgraderingsprøver består i ordinærporten og må også kjøres i ekte SQL Server-CI.
Tidlige sandboxforsøk på restore/testhost og NU1900 er ikke bestått auditbevis;
senere låste restore kjørte med aktiv audit og fungerende nettverk.

Edge/SQLite med kontrollert tilgang og mottaker beviser ikke Entra,
gjestebrukertilgang, Azure SQL, M365 eller faktisk ekstern levering. Ingen
produksjonsutsending, utrulling, ekstern tilgangsendring, commit, push eller PR
er utført av byggeren. #110 og senere EV-tickets beholder sitt omfang.
