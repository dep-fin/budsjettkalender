# UX18: Atelier: samlet kompatibilitets- og tilgjengelighetsakseptanse for #75

Blocked by: #92

Hovedoppgave: #75
Plan-ID: UX18. Avgrenset leveranse, men ikke startklar før Blocked by er lukket.
Dekker historier i #75: 1, 2, 6, 20, 24, 29, 43, 44, 45, 46, 47, 48, 68, 69, 71, 74.

## Problem Statement

Små leveranser må til slutt prøves sammen slik at modernisering ikke fjerner tidligere funksjoner eller tilgangsvern.

## Solution

Gjennomfør samlet, dokumentert akseptanse av Atelier-kandidaten mot #75 og de eksisterende funksjonsgrensene.

### Akseptansekriterier

- [ ] Kravkartet for #75 historier 1–89 peker til levert oppgave/testbevis eller uttrykkelig eksisterende/utsatt omfang.
- [ ] Hovedscenario dato → forslag → kø → godkjenning → samme frist i Kalender/Budsjettår passerer.
- [ ] Navigasjon, gamle innganger, filtre, alle tre kalenderflater, tidslinje, fasemal, regelbygger/listesortering, dokumentflyt og øvrige adminområder prøves samlet.
- [ ] Tastatur/fokus/Escape/feil, skjermlesernavn, kontrast/zoom og mobil kontrolleres i relevante hovedflyter.
- [ ] Ingen skjulte frister, tellinger, ventemerker, interne gjøremål eller feedtokens lekker mellom roller/grupper.
- [ ] Relevante ordinære, SQL Server- og Chromium-jobber er grønne på faktisk kandidat, med Standards-/Spec-review og nødvendig sikkerhetsaudit.
- [ ] Datert overlevering skiller levert app, prototype, utsatte oppgaver og eksterne porter; #75 lukkes først ved faktisk avtalt kodeakseptanse.

## User Stories

1. Som bruker vil jeg kunne bruke hele løsningen på tastatur og mobil, slik at moderniseringen er tilgjengelig.
2. Som bruker vil jeg beholde gamle innganger og funksjoner, slik at arbeid ikke brytes.
3. Som bidragsyter vil jeg få samme fulle godkjenningsløp fra dato som fra vanlig skjema, slik at innsending er pålitelig.
4. Som administrator vil jeg se samme fristdata og regelsett i alle relevante flater, slik at kopier ikke oppstår.
5. Som produkteier vil jeg se faktisk testbevis og kjente grenser, slik at prototypebilder ikke forveksles med ferdig app.
6. Som driftsansvarlig vil jeg beholde egne pilot-/miljøporter, slik at lokal demo ikke erklæres produksjonsklar.

## Implementation Decisions

- Dette er siste samordning, ikke utsettelse av grunnleggende regresjon, tilgjengelighet eller sikkerhet fra tidligere tickets.
- Prøv faktiske Blazor-handlinger mot Kestrel og eksisterende tjeneste-/SQL Server-grenser.
- #56 og andre pilot-/Office-/Entra-porter består og lukkes ikke av denne oppgaven.
- AD01/AD02 er egne, senere rolleforvaltningsoppgaver; #75s prototypevalg om utnevnelse er allerede dokumentert, og UX17 leverer oversikten.

## Testing Decisions

- Viderefører avklart testgrense fra #75: eksisterende reelle nettlesertester mot Kestrel/Blazor er hovedgrensen, med dagens tjenestekontrakter for roller, synlighet og publisering. Test ekstern atferd og lagret resultat, ikke privat tilstand eller CSS.
- Samordne eksisterende browser-suite og reelle tjenestekontrakter, uten ny parallell mock-akseptansearkitektur.
- Dokumenter testmiljø/revisjon og rett blokkerende funn med regresjoner; reell Entra/Azure/Outlook dokumenteres bare av egne miljøbevis.
- Før ferdigstilling: relevante regresjoner, Standards-/Spec-review, nødvendig sikkerhetsaudit og grønne ordinære/SQL Server-/nettleserjobber etter prosjektets regler. Lokal demo erstatter ikke Azure/Entra/Outlook-bevis.

## Out of Scope

- Produksjonsutrulling eller generell mergeautorisasjon.
- Å lukke pilotplan #38/#56/#57 eller fremtidig AD02 uten deres egne kriterier.
- Automatisk publisering, stille POL-valg, endret synlighet ved endringsforslag eller uautorisert produksjonsutrulling.

## Further Notes

- Gjeldende samlet spesifikasjon og beslutninger finnes i #75. [Sortert Atelier-referanse](https://github.com/depmartin/Budsjettkalender/tree/36dd6f06e471113b98571d24ebd93dd044b848fc/docs/prototypes/atelier-samlet-2026-10-27) er visuell primærkilde, ikke produksjonskode eller appakseptanse.
- Implementer én ticket om gangen fra oppdatert hovedgren. Den nummererte UX-rekken er bevisst serialisert som leveranseporter; ikke alle porter betyr en isolert teknisk avhengighet. Ikke start etterfølger før forrige leveranse er verifisert/avsluttet.
- Les hele #75, denne ticketen og kommentarer, gjeldende AGENTS, ordliste, ADR-er og reell branch/worktree-status før arbeid. Bevar andre uferdige checkouter.
- Blocked by brukes som eksplisitt avhengighet fordi tilkoblet verktøy ikke eksponerer native GitHub-avhengighetsmutasjoner. Når forutsetninger er lukket, verifiser status og merk neste kodeoppgave ready-for-agent; beslutningsoppgave blir ready-for-human når den faktisk kan tas.
- En ferdig ticket er ikke merge-/deployautorisasjon for andre tickets eller hele #75. Oppdater hovedoppgavens plan ved levering.
